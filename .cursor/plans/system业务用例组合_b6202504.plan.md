## 用例设计（001~010）
- **TC-SYS-BIZ-001 用户完整生命周期**
  - 链路：登录 -> 新增用户（含 dept/role/post）-> 修改用户字段 -> 列表/DB 校验 -> 删除用户 -> `del_flag='2'` 校验。
  - 关键断言：每步 `code==200`；更新字段 DB 回查一致；删除后软删标记正确。

- **TC-SYS-BIZ-002 角色授权闭环**
  - 链路：新增角色 -> 新增用户绑定该角色 -> `allocatedList` 可见 -> 用户去角色/改角色 -> `unallocatedList` 可见 -> 清理。
  - 关键断言：分配与去分配前后列表命中符合预期；关联表数量变化正确。

- **TC-SYS-BIZ-003 岗位授权闭环**
  - 链路：新增岗位 -> 新增用户绑定岗位 -> DB 关联存在 -> 解绑岗位 -> 关联消失 -> 删除岗位。
  - 关键断言：`sys_user_post` 关联计数从 `>=1` 到 `0`；删除岗位返回成功。

- **TC-SYS-BIZ-004 角色删除保护链路**
  - 链路：角色已被用户占用时删角色应失败 -> 删除用户并清理残留绑定 -> 再删角色成功。
  - 关键断言：失败场景返回 `code==500` 且 `msg` 含“已分配/不能删除”；解绑定后删除成功。

- **TC-SYS-BIZ-005 岗位删除保护链路**
  - 链路：岗位已被用户占用时删岗位应失败 -> 删除用户并清理绑定 -> 再删岗位成功。
  - 关键断言：与 004 同类约束断言，覆盖岗位维度。

- **TC-SYS-BIZ-006 角色状态对授权行为影响**
  - 链路：新增角色并绑定用户 -> 改角色状态为停用 -> 执行授权相关查询/变更 -> 恢复正常状态。
  - 关键断言：停用后行为与产品规则一致（至少保证接口返回与状态字段一致、无脏状态）。

- **TC-SYS-BIZ-007 数据权限切换稳定性**
  - 链路：同一角色连续切换 `dataScope=1/2/3/4/5` -> 每次查详情/DB 验证 -> 最终删除角色。
  - 关键断言：每次切换成功且最终状态与最后一次设置一致，无中间写入丢失。

- **TC-SYS-BIZ-008 组织树+用户归属联动**
  - 链路：新增部门（建议父子结构）-> 在新部门新增用户 -> 修改用户部门归属 -> 删除部门（按是否仍占用断言失败/成功）。
  - 关键断言：部门占用约束生效；迁移后归属一致；最终可清理。

- **TC-SYS-BIZ-009 公告发布全链路**
  - 链路：新增公告 -> 列表按标题/状态命中 -> 修改标题/内容/状态 -> 详情校验 -> 删除公告。
  - 关键断言：列表与详情字段一致；删除后查询不存在或不命中。

- **TC-SYS-BIZ-010 鉴权统一防护回归**
  - 链路：对用户/角色/岗位/部门/公告关键写接口统一执行“无 token”调用。
  - 关键断言：全部请求被拦截（`code!=200`）；错误语义包含鉴权关键词。

## 公共实现规范（保证稳定性）
- 统一使用唯一标识（`uuid` 前缀）创建测试数据，避免并发污染。
- 每条业务流使用 `try/finally` 逆序清理，优先删用户，再清理关系，再删角色/岗位/部门/公告。
- 对若依已知行为（逻辑删除后关系残留）保留 `purge_sys_user_bindings` 兜底。
- 所有关键步骤加 Allure 附件：入参摘要、响应摘要、DB 回查结果，便于失败定位。

## 执行与验收
- 执行顺序：先单条逐个跑通（`-k TC-SYS-BIZ-00X`），再跑 `test_system_business_flows.py` 全量。
- 验收标准：
  - 10 条用例均可独立执行且可重复执行。
  - 失败信息可定位到具体步骤（接口/断言/DB）。
  - 执行后环境无脏数据（角色、岗位、用户、公告、部门均可回收）。

## 风险与规避
- 测试环境基础数据不足（角色/岗位/三级部门缺失）导致跳过：在用例内显式 `pytest.skip` 并附加原因。
- 状态类用例受后端实现差异影响：先以“行为一致性 + 返回码 + 字段落库”为最小稳定断言。
- 多用例共享数据导致串扰：严禁跨用例复用实体 ID，统一每条用例自建自清。
